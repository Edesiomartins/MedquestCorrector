# Universal Discursive Import Design

Date: 2026-09-10
Status: Approved in chat, pending written-spec review

## 1. Goal

Allow MedquestCorrector to correct handwritten **discursive-only external exams** that were not generated by MedquestCorrector.

The professor uploads the original blank discursive exam as PDF or DOCX. The system detects each question and its answer area, shows a visual confirmation screen, saves the approved geometry as a layout manifest, and later applies the existing HTR V2 pipeline to scanned answered copies.

This feature is only for discursive exams. The current practical-exam flow must remain unchanged.

## 2. Scope

The first release supports:

- Discursive-only source files.
- PDF and DOCX as source formats.
- One or more questions per document.
- Question numbers that may start at any value, for example Q38.
- Automatic detection of question blocks and answer regions.
- Visual confirmation and manual adjustment before the layout is accepted.
- Saving the confirmed geometry as a reusable manifest.
- Applying HTR V2 to scanned answered exams using the confirmed manifest.
- Qwen3 VL 32B Instruct as the normal low-cost VLM through the existing configurable vision-model setting.
- Selective escalation of only difficult/low-confidence answer crops to a stronger configured VLM, such as GPT-5.6 Sol.
- Erasure metadata preserved by HTR for discursive review.

## 3. Non-goals

This release does not:

- Modify practical-exam behavior.
- Detect or grade multiple-choice questions.
- Accept a mixed objective + discursive document as the primary workflow.
- Attempt fully automatic grading without professor confirmation of the detected geometry.
- Require external exams to be generated by MedquestCorrector.
- Replace the existing grading rubric workflow.
- Change practical matcher rules.

## 4. User flow

### 4.1 Register external discursive layout

1. Professor chooses **Import external discursive exam**.
2. Uploads a PDF or DOCX containing only the discursive questions.
3. Backend normalizes the document to page images for geometry detection.
4. Detector identifies question labels/numbers, question text blocks, and candidate answer regions.
5. Frontend displays each detected question over the page preview.
6. Professor confirms or adjusts the answer region for each question.
7. The system validates that every accepted question has a unique number and a valid answer region.
8. The approved layout is saved as a manifest linked to the exam/template.

### 4.2 Correct answered scans

1. Professor uploads scanned answered copies.
2. The existing student/page identification flow runs normally.
3. The confirmed manifest supplies the answer boxes.
4. HTR V2 renders high-resolution crops, detects blank boxes, builds contact sheets, and performs one multimodal transcription call per student/page using the configured normal VLM.
5. Only answers that trigger the selective quality gate are re-read from the individual crop by the configured stronger VLM.
6. The existing discursive grader applies the rubric to the selected/final transcription.
7. Questions with erasure remain marked for professor review.

## 5. Detection strategy

Use a conservative detector with professor confirmation, not a fully autonomous layout guesser.

### 5.1 Preferred structural signals

For PDF or rendered DOCX pages, use combinations of:

- Explicit labels such as `Questão 38`, `QUESTÃO 38`, `Q38`, or equivalent normalized variants.
- Text block geometry from the document/parser when available.
- Horizontal answer lines below the question.
- Large white answer areas below the question text.
- Vertical spacing between the end of one question and the next question label.
- Page boundaries.

### 5.2 Candidate answer region

For each detected question, the detector proposes a rectangle beginning after the question text and ending at the earliest reliable boundary among:

- the next question label;
- the bottom of the recognized answer-line group;
- the page content boundary;
- an explicit answer-area element from DOCX structure when available.

The detector must never silently assign overlapping answer boxes to two questions.

### 5.3 DOCX handling

DOCX may provide stronger structure than raster-only detection. The implementation should prefer document structure where reliable, then render the result to page coordinates used by the manifest.

The backend may convert/render DOCX for preview, but the persistent output of detection must be the same geometry manifest format used by the PDF path.

## 6. Confirmation UI

The confirmation screen is a safety gate.

For each page it must show:

- page preview;
- detected question number;
- highlighted proposed answer rectangle;
- ability to resize/move the rectangle;
- ability to correct the question number;
- ability to remove a false detection;
- ability to add a missed question region.

The professor must explicitly confirm the layout before it can be used for grading.

Validation before confirmation:

- no duplicate question numbers;
- no zero/negative question numbers;
- every question has a non-empty answer rectangle;
- rectangles stay inside page bounds;
- no invalid geometry;
- warning for suspicious overlap.

## 7. Manifest

Reuse the current HTR manifest concepts rather than create a parallel geometry system.

Each confirmed question region must contain at minimum:

- page index;
- real question number;
- normalized or page-relative rectangle coordinates;
- optional source confidence from the detector;
- optional detector provenance, for example `docx_structure`, `text_geometry`, `answer_lines`, or `manual`.

The saved manifest becomes the source of truth for answered scans.

## 8. HTR V2 integration

The universal-discursive mode must feed the **same downstream question shape** already consumed by the grading pipeline.

HTR V2 remains responsible for:

- rendering answer crops at high resolution;
- blank detection;
- preserving question numbers from geometry;
- building one or two contact sheets;
- sending contextual page image + contact sheets in one multimodal request;
- validating exact question coverage;
- falling back safely when an expected operational failure occurs.

The universal import feature must not duplicate HTR logic.

## 9. Vision-model strategy

The model remains configuration-driven. Do not hardcode Qwen or Sol into business logic.

Recommended production configuration after current tests:

- normal VLM: `qwen/qwen3-vl-32b-instruct`;
- stronger escalation VLM: a separately configured stronger model, initially GPT-5.6 Sol if desired.

The normal path sends the page/context sheets once to the low-cost model. The expensive model is not part of the ordinary path and must only receive a difficult individual answer crop after the quality gate triggers.

## 10. Erasures

HTR must preserve erasure as explicit evidence instead of omitting crossed-out text.

Extend the normalized transcription result with optional fields:

- `has_erasure: bool`
- `erased_text: str`

For discursive exams:

- erasure does **not** automatically zero the question;
- `has_erasure=true` marks the question for professor review;
- the final visible transcription should still represent the student's intended non-erased answer when readable;
- `erased_text` is supplementary evidence for review.

Practical-exam erasure rules are outside this feature and the practical flow remains unchanged in this implementation.

## 11. Low-confidence handling and selective escalation

Selective escalation is part of the first release but remains behind configuration so it can be disabled independently.

The quality gate should escalate only when one or more of the following occurs:

- `reading_confidence=baixa`;
- `[ilegível]` is present;
- model reports unresolved ambiguity in `reading_notes`;
- schema is valid but the normalized reading carries an explicit uncertainty marker such as `[?]`;
- another narrowly defined quality rule is explicitly configured and tested.

Do not send every answer to the expensive model.

When escalation triggers:

1. Send only the high-resolution crop for that question to the stronger VLM.
2. Keep the transcription stage blind to answer key/rubric.
3. Preserve both the original normal-model reading and the escalation reading for audit metadata.
4. Use the stronger reading as the final transcription only when the escalation call succeeds with valid schema.
5. If escalation fails, keep the normal-model reading, mark the question for review, and do not fail the whole student's page.
6. Erasure itself does not automatically trigger Sol; erasure is a review signal unless the reading is also uncertain.

## 12. Failure handling

Expected behavior:

- Source-file parsing failure: stop layout creation and show a clear error.
- No questions detected: do not invent geometry; require manual addition or a different source file.
- Partial detection: show detected items and allow manual completion.
- Invalid confirmed geometry: block save until corrected.
- HTR V2 operational failure after a manifest exists: preserve the existing safe fallback behavior.
- Selective escalation failure: retain the normal VLM reading and require review rather than reprocessing the full page.
- Unexpected programming errors must not be silently swallowed as normal fallback.

## 13. Observability

Keep layout correctness and HTR metrics separately understandable, but universal-import runs should expose enough metadata to debug geometry and cost problems.

Useful non-sensitive logs include:

- template/exam identifier;
- source format;
- pages detected;
- question numbers detected;
- detector strategy used;
- number of manual adjustments;
- HTR strategy used;
- elapsed time;
- normal model used;
- number of selectively escalated questions;
- escalation model used;
- token usage for normal and escalation calls when provided by OpenRouter.

Do not log student answers, prompts, images/base64, API keys, or unnecessary personal data.

## 14. Data/privacy

- Do not increase retention of page images beyond current product behavior unless explicitly required.
- Do not place answer keys or grading rubrics into the HTR transcription prompt.
- Layout detection may inspect the blank exam content, but grading criteria remain isolated from visual transcription.
- Saved manifests contain geometry and question numbering, not student handwriting.

## 15. Testing

Use TDD for implementation.

Minimum automated coverage:

### Detector

- single question with lined answer area;
- multiple questions on one page;
- questions spanning multiple pages;
- numbering beginning above 1, for example Q38;
- non-contiguous numbers;
- answer area ending at the next question;
- answer area ending at page bottom;
- blank-space answer area without horizontal lines;
- duplicate/invalid detections rejected;
- partial detection remains editable rather than fabricated.

### DOCX/PDF

- equivalent manifest shape for both supported formats;
- DOCX structural detection when available;
- PDF geometry fallback.

### Confirmation/save

- manual move/resize persists corrected coordinates;
- corrected question number persists;
- manually added question persists;
- invalid geometry cannot be saved.

### HTR integration

- confirmed universal manifest enters existing HTR V2 path;
- practical flow is unchanged;
- question numbers are preserved end-to-end;
- erasure metadata survives normalization and reaches review state;
- low-confidence answer triggers exactly one selective crop escalation when enabled;
- high/medium-confidence answer does not trigger escalation;
- escalation failure preserves the normal-model reading and marks review;
- no answer key/rubric leaks into normal or escalation visual transcription.

## 16. Rollout

1. Implement behind a universal-discursive-import feature flag, disabled by default.
2. Keep selective escalation behind its own feature/configuration flag.
3. Validate with the provided style of one-question discursive sheet.
4. Validate with a multi-question external discursive exam.
5. Compare detected boxes visually against professor-confirmed boxes.
6. Run answered-scan HTR tests with Qwen.
7. Enable selective escalation on controlled tests and measure how many questions reach the stronger model, quality gain, latency, and cost.
8. Only then enable the universal import for normal production use.

Rollback must be possible by disabling universal-discursive-import and/or selective escalation without affecting current practical or existing HTR V2 exams.

## 17. Success criteria

The feature is successful when a professor can:

1. upload a discursive-only PDF or DOCX not generated by MedquestCorrector;
2. see correctly detected question numbers and proposed answer areas;
3. correct any detection mistakes visually;
4. save the layout;
5. upload answered scans;
6. have those answers read through the existing HTR V2 pipeline with the normal low-cost VLM;
7. automatically escalate only objectively difficult readings to the configured stronger VLM;
8. review erasures/low-confidence cases without altering the practical-exam workflow.
